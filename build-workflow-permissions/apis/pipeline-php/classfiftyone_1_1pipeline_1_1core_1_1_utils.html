◆ getFlowData()

fiftyone\pipeline\core\Utils::getFlowData ( )
static

The Flow Data the last call to processWebRequest() processed, or null when there has been none.

A PHP that builds its state afresh for every request starts each one with none. A PHP that serves one request after another, as a worker does, keeps it between them, so a request there that has not called processWebRequest() gets the previous request's Flow Data. Call processWebRequest() first in every request that reads it.

So these methods suit a PHP that handles one request at a time in each process or thread. In a runtime that interleaves requests in one thread, such as one that runs them as coroutines, the next request's call to processWebRequest() closes and replaces the Flow Data an earlier request may still use. Code there passes on the Flow Data that processWebRequest() returns instead of reading it here.

Answer a request for the client-side JavaScript with the JavaScript the Pipeline's JavaScript Builder Element writes, and the cache headers of the web integration specification.

The FlowData holds the request's Evidence and has not been processed, because the ETag is a hash of the Evidence the request supplied, and processing adds Evidence, such as the session id the Sequence Element gives a request without one. The ETag is weak, W/"...", because the response can change while the Evidence does not, for example when the data file is updated.

A request whose If-None-Match header matches the ETag, by the weak comparison of RFC 9110 section 13.1.2, is not processed. It gets a 304 when it is a GET or HEAD and a 412 otherwise. An If-None-Match that is neither "*" nor a list of entity tags matches nothing. Any other request is processed and gets a 200 with Cache-Control 'max-age=1800, private', or the max age given, and the ETag, or 'private, no-cache' and no ETag when processing recorded errors. When the JavaScript Builder Element itself failed, the script is empty.

Handle a web request with the Pipeline.

A Flow Data is created, the request's Evidence is added to it with Evidence::setFromWebRequest(), and it is processed. The processed Flow Data is then kept, where any other part of the application reads it with getFlowData() without being handed it. It is closed when PHP finishes the request, or when a later call replaces it, as in a PHP that serves one request after another. There it is kept until that later call, so see getFlowData() for a request that does not call this.

A Flow Data is not safe to use from several threads at once, and must not be used by two threads at once. The caller is responsible for any locking, so code that hands the Flow Data to another thread coordinates that itself.

Requests for the client-side JavaScript and JSON need a Flow Data that has not been processed, so answer those with javascriptResponse() and jsonResponse() instead.
